# Advisor Workflow

Writing rule: `HZ-SYN-004`. Keep the full logic. Give the user the answer in short, plain words.

Use this workflow to think through personalized advice and linked business choices. Match its depth to the request. Do not force a full limiting-factor audit or a new test onto a question that the supplied facts already settle.

## 1. Define The Outcome

Translate the request into one observable economic or operating result. Separate the desired result from the proposed tactic. Capture the time horizon, current baseline, target, and non-negotiable constraints when known.

## 2. Build The Constraint Map

Use only relevant business evidence. A typical commercial map is:

```text
reachable market → engaged leads → scheduled → showed → bought
→ activated → retained/expanded → gross profit → cash timing
```

Add delivery capacity, quality, team, or regulatory steps only when they are material. For each step record volume, conversion, delay, capacity, cost, and evidence quality. Do not call the smallest percentage the constraint automatically; estimate the downstream economic gain available from relieving it.

## 3. Make A Constraint Call

State:

- the binding constraint;
- the evidence for it;
- the strongest competing explanations;
- why those alternatives are not first;
- what fact would change the call.

If evidence is insufficient, prescribe a measurement step rather than a business tactic.

## 4. Select Modes

Read `mode-index.md`. Scan every mode that could materially affect the result before narrowing the work. A mode is a doctrine and workflow boundary, not a separate advisor.

- For a narrow request, start with the most relevant reference. Follow another when it could change the answer.
- For a complex decision, inspect each area that materially affects the choice. The current mode count is not a limit on the audit.
- For a full business audit, map the important links across the business, then focus the work on the main limiting factor and a clear sequence.

Do not load every doctrine file just because its mode was scanned. Read the full references only for modes selected for deep inspection. If evidence from another mode changes the constraint call, update the call instead of defending the first route.

Typical sequences:

- diagnose → offer-economics → demand;
- diagnose → sales → offer-economics when objections expose a true offer weakness;
- diagnose → customer-value → offer-economics for expansion economics;
- diagnose → team-operations only after a people or operating-system constraint is evidenced.

## 5. Retrieve Bounded Evidence

Read the relevant task guide as well as general diagnosis. A correct bottleneck label is not enough to design the fix. For customer proof, use [doctrine/proof-review.md](doctrine/proof-review.md) and its linked collection guide.

Start source search with a small packet. Six results is a starting size, not a ceiling. Search snippets locate evidence; they are not the full evidence. Open the cited page or section and enough nearby context to check the rule and its limits. Broaden weak searches or follow related sources when they could change the advice.

When the user asks whether a source supports a claim, find that actual teaching before judging it. A related principle alone does not show what the author said. Use the relevant linked guide to find the passage and its conditions, then check the original. Separate a source's shortcut or example from the result of applying it to these facts.

Keep the packet bounded:

- doctrine rule IDs and summaries;
- exact source locators;
- relevant business-authority excerpts or facts;
- page-image or public-video pointer when visual meaning matters;
- explicit uncertainty and conflict notes.

Never load an entire source dump as the default retrieval strategy.

## 6. Decide And Sequence

Prefer the intervention that combines direct impact on the binding constraint, high expected economic gain, fast and observable feedback, low irreversible cost, stage fit, operational feasibility, and claims and safety compliance.

Reject attractive work that does not address the main problem or adds needless complexity. For lead growth, compare the return from improving the working path with the return from a new one. If dependence on one source is itself the problem, check whether the next path removes that dependence. Use HZ-DEM-002 and its linked guide; do not apply a fixed channel order to every goal.

For a choice driven by numbers, keep each measure tied to its unit, group and time span. Compare like with like. Use a calculator or a small read-only calculation to verify the math. Substitute a proposed threshold back into the formula and check whether it matches or beats the old result. Check the words around the answer as well as the arithmetic. A correct amount with the wrong label can still lead to the wrong choice.

## 7. Define The Test

Define a test that fits the known facts and the request. Name the owner, action and useful result. Add timing, cost and safety limits where they matter. Label a proposed test size as your suggestion, not a source rule. Base it on capacity or explain the choice. If capacity is unknown, start with a small feasible step rather than invent a mandatory quota. Keep every target and time window consistent. Count useful outcomes, not activity for its own sake.

## Repeated Use

At the next consultation, inspect the business context without writes and read the relevant current authorities. Compare the new evidence with the prior decision. Continue, change or stop; do not repeat the same advice from stale context. Missing profile sections do not block a choice the known facts already settle.
